这个工具最初的需求并不复杂：读取 Unity 构建出来的 AssetBundle，显示每个包的大小、包含的资源和依赖关系。

真正开始做以后，我才发现“把数据画成节点”只是最表面的一层。路径格式不统一，主 Manifest 和单包 Manifest 的内容也不一样；有些包名长得离谱，有些包干脆没有 Manifest。等数据量上来以后，还会碰到节点布局、搜索卡顿，以及 GraphView 实验性 API 的各种不兼容。

这篇文章记录的就是这些问题，以及 AB Graph 一路修修补补变成可用工具的过程。

## 最初的构想

AssetBundle 问题通常不是单个包的问题，而是关系问题：

- 哪些包特别大？
- 一个包里到底塞了哪些资源？
- 谁依赖了谁？
- 某个公共包被多少业务包引用？
- 搜到一个资源后，它究竟被打进了哪个包？

表格适合统计大小和数量，却不擅长表示依赖网络。所以最初的界面很自然地靠近 Shader Graph：一个包对应一个节点，依赖关系就是节点之间的连线。

第一版脑图大致如下：

![](IMG-20260806133350075.png)

当时我的心理预期是：“GraphView 连 Shader Graph 都能做，这个应该很顺。”后来事实证明，GraphView 的“能做”和“顺手”完全是两回事。

最后还是选了 `UnityEditor.Experimental.GraphView`。虽然名字里明晃晃地写着 Experimental，但它至少省掉了这些基础工作：

- 节点、端口和边的基础模型；
- 画布平移和滚轮缩放；
- 节点选择、框选与拖动；
- MiniMap；
- `FrameAll`、`FrameSelection` 等视图定位能力。

工具整体位于 Editor 目录，只参与编辑器编译，不会进入运行时包体。主要文件职责如下：

```
AssetBundleGraph/Editor/
├─ AssetBundleData.cs          数据模型、Manifest 解析、依赖反向索引
├─ AssetBundleNode.cs          单个 AB 节点、端口、资源信息窗口
├─ AssetBundleGraphView.cs     画布、布局、搜索、按需连线、统计面板
├─ AssetBundleGraphWindow.cs   EditorWindow、工具栏、信息栏、菜单入口
├─ DraggablePanel.cs           可拖动浮动面板基础实现
└─ AssetBundleGraph.uss        节点、端口和画布样式
```

节点图之外，我还补了几组可以单独运行的批处理工具：

- `ABStats.bat / ABStats.ps1`：递归统计 AB 数量与大小分档；
- `FindGUID.bat / FindGUID.ps1`：根据 GUID 找资源路径；
- `FindGUIDRefs`：查找哪些 Unity 文本资源引用了指定 GUID；
- `FindGUIDAll`：在指定目录全部文件中搜索 GUID。

## 具体实现

### 识别 AssetBundle

工具没有硬编码 `.ab` 扩展名。项目里的包实际使用 `.bnk`，Unity 本身也允许 AssetBundle 使用任意扩展名。

最初的识别规则是：

1. 扫描目录中的 `*.manifest`；
2. 去掉 `.manifest` 后缀；
3. 如果同名文件存在，就认为它是一个 AssetBundle；
4. 如果同名文件不存在，则将该 Manifest 视为主 Manifest。

后来又发现 `init.bnk` 这类包没有对应 Manifest。只从 Manifest 反推会漏包，于是补充了第二轮扫描：递归扫描实际文件，将没有同名 Manifest 的候选包也加入节点集合，只是它们没有 Assets 和依赖详情。

### 解析 Manifest

Manifest 主要分为两类。

#### 单包 Manifest

单包 Manifest 主要包含：

```
Assets:
- Assets/Textures/A.png
- Assets/Prefabs/B.prefab
Dependencies:
- G:/Build/OutputCache/shared.bnk
```

![](IMG-20260806133629455.png)

解析器使用状态机区分 Header、Assets、Dependencies 三个区段，将资源路径和依赖路径分别写入 `BundleNodeData`。

#### 主 Manifest

主 Manifest 负责描述跨包依赖。工具解析后，将主 Manifest 中的数据合并进各个节点的 `Dependencies`。

一开始依赖边始终是 0。原因是主 Manifest 被当作“没有对应包文件的无效 Manifest”跳过了。

修复后，解析流程变为两遍：

1. 第一遍建立 Bundle 节点，同时收集主 Manifest 的依赖映射；
2. 第二遍将依赖映射合并到节点数据，并反向生成 `Dependents`。

### 资源信息窗口

单击节点后，会在它下方打开一个可拖动的信息窗口。节点名不再重复占位置，窗口里只放排查时真正会看的内容：

- 包大小；
- 全部资源列表；
- 每个资源的名称和占用空间；
- 依赖信息；
- 滚动条。

![](IMG-20260806134552468.png)

第一版的“查看全部资源”会再弹出一个窗口。实际用起来，两个浮窗很容易互相遮挡，还得来回整理位置。我后来把资源列表直接塞回同一个窗口，内容放不下就滚动。

点击具体 Asset 时，工具调用 `AssetDatabase.LoadAssetAtPath<UnityEngine.Object>`：

- 如果原始资源存在于当前 Unity 工程，则选中并在 Project 中定位；
- 如果只有 AB 文件、原始资源不在工程中，则输出明确警告，而不是静默失败。

### 依赖网络

早期版本进入工具时就创建全部依赖边。面对数千条依赖，画面既混乱又容易出现残留边、重复边和性能问题。

更严重的是，聚焦一个节点时，虽然只想看它的一层关系，但 GraphView 中已经存在全部边。通过 `display:none` 筛选时出现过“无主边”：两个可见邻居之间的历史边也留在画面里，肉眼看起来比依赖数多。

这条路继续修补意义不大，我索性改成按需连线：

```
加载目录
  -> 只解析数据、创建节点
  -> 默认不创建任何边

双击或右键展开节点
  -> 收集中心节点的 Dependencies
  -> 收集中心节点的 Dependents
  -> 只为这些直接关系创建 Edge

退出展开
  -> 删除本次创建的全部 focusEdges
```

改完以后，单层网络里的每个邻居只会保留一条与中心节点相连的边：

![](IMG-20260806134507470.png)

布局规则也与端口方向统一：

- 被依赖节点在中心上方；
- 依赖节点在中心下方；
- 同一行按包大小从左到右降序排列；
- 节点之间保留足够水平、垂直间距；
- 展开时只显示中心节点实际关联的节点和边。

双击节点可以直接展开网络；右键菜单保留“打开信息窗口”“展开依赖网络”“定位到节点”三个自定义选项，并禁止手动连线以及删除、复制等默认编辑行为。

![](IMG-20260806134639564.png)

### 展开历史与返回上一级

分析依赖时经常会从 A 跳到 B，再从 B 跳到 C。为了避免每次都回到总览重新找，工具用 `Stack<string>` 保存展开历史：

```
展开 A -> history=[]
展开 B -> history=[A]
展开 C -> history=[A,B]
返回   -> B
返回   -> A
```

这里还出过一个挺绕的小 bug：返回时会再次调用 `FocusNetwork`，被当成新的展开操作，历史栈随即清空，所以只能返回一次。最后加了一个“正在返回”的状态标记，让返回动作不再压栈，也不会清空历史。

改完以后，从 A 查到 B、再查到 C，终于可以顺着原路一级一级退回去了。

### 初始视图修正

默认界面最初尝试按依赖深度做树状布局，但上千个包的依赖不是树，而是高度交叉的图。结果是列高极不均衡，也无法快速发现大包。

后来我放弃了树状总览，默认视图改成更直接的矩形网格：

- 全部节点按包大小降序；
- 每行固定数量；
- 从左到右递减；
- 满一行后进入下一行；
- 默认无连线。

![](IMG-20260806134818881.png "初始视图")

![](IMG-20260806134849469.png "双击展开某个节点后，图中不规则的连线说明两节点双向依赖")

实际排查时，我通常先从总览里找出大包，再双击展开它的一层依赖。这个顺序比一上来面对整张网清楚得多。

### 统计信息

顶部信息栏显示：

- AB 总大小；
- AB 包数量；
- 资源数量；
- 1~10MB 包数量；
- 10~20MB 包数量；
- 大于 20MB 包数量。

点击大小分档会打开对应包列表，按大小降序展示名称和体积。再次点击同一项会关闭窗口。

这些列表窗口和展开网络后的依赖信息窗口都支持拖动。拖动实现中曾出现窗口第一次移动时瞬移到左上角的问题：面板可能通过 `right/bottom` 锚定，而代码却直接读取未设置的 `left/top`，结果得到 0。

修复方式是在鼠标按下时通过 `worldBound` 计算面板相对父容器的真实位置，再转成显式 `left/top` 后开始拖动。

窗口缩放也做过一版，但右下角把手会跟着窗口尺寸变化，形成反馈循环，拖起来一直抖。我折腾了一阵，最后还是把缩放删了，只留下稳定的拖动。一个不可靠的高级功能，确实不如没有。

### 资源搜索与性能优化

最早的资源搜索是实时的：输入每个字符都遍历全部节点和全部 Assets，然后重建结果 UI、修改所有节点透明度。

在 1000 多个包、数万个资源的场景中，体验很卡。

这块前后改了三次：

1. 加入 300ms 防抖；
2. 加载时预建资源名到 Bundle 的索引；
3. 最后改为点击“搜索”按钮或按回车后执行。

索引结构类似：

```
asset_name(lowercase) -> [bundleA, bundleB, ...]
```

![](IMG-20260806135520039.png)

搜索结果窗口放在搜索框下方。我把它加宽、加高，并补上横向和纵向滚动，不然长路径挤在一起很难看清。点击结果里的包名，会直接聚焦对应节点。

## 独立 AB 统计脚本

有时候只想先看一眼包的数量和大小，为此再打开 Unity 有些麻烦。我另外写了 `ABStats.bat + ABStats.ps1`，直接递归统计指定目录及子目录中的 AB 包。

调用方式：

```
ABStats.bat D:\任意待分析目录
```

统计分档为：

- 小于等于 1MB；
- 1~10MB；
- 10~20MB；
- 大于 20MB。

脚本所在位置可能位于 Unity 工程 `Packages` 的多层子目录中，而待分析目录可以是任意位置。输出目录不是输入目录，而是根据脚本自身位置向上寻找 `Packages`，然后写入其同级目录：

![](IMG-20260806135719868.png)

## GUID 引用辅助脚本

Unity 的引用关系可以概括为：

```
B.png.meta 中保存 B 自己的 GUID
A.prefab 引用 B 时，A.prefab 文本中保存 B 的 GUID
```

我于是又写了三类脚本：

- GUID 到资源路径：搜索 `.meta` 中的 `guid:`；
- 查谁引用 GUID：搜索 `.prefab`、`.unity`、`.mat`、`.asset` 等文本资源内容；
- 全目录搜索 GUID：不限制扩展名，扫描所有文件。

这些脚本和 AB Graph 没有代码层面的依赖，但实际排查时经常会搭配使用。需要找 GUID 时直接跑脚本，比在节点图里硬翻省事得多。

AB Graph 最初只是一个“像 Shader Graph 的节点图”。改到现在，它可以按大小浏览、按资源搜索、按需展开直接依赖，也能查看包内资源；节点图之外，还有统计和 GUID 查询脚本补足排查链路。

回头看，最有用的一次改动反而是“默认不画边”。全量依赖乍看很完整，真正面对上千个节点时只剩一团线。先找出大包，再展开它的一层关系，问题才更容易看清。
